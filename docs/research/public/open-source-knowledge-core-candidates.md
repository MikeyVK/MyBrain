# Open-source knowledge-core candidates

**Status:** research  
**Version:** 1.0  
**Last Updated:** 2026-10-24

## Purpose

Assess existing open-source knowledge applications and reusable engines against MyBrain's accepted conceptual principles, separating implemented capabilities from modeling, integration and unproven guarantees.

## Scope In

Claim registration, reusable definitions and their applications, contextual authoring, history, temporal interpretation, provenance, retrieval evidence, access, preservation, licensing and proposed synthetic validation.

## Scope Out

Product adoption, a prescribed ontology or stack, live ingestion, original email/NAS implementation, deployment, installation and executed candidate trials.

## Summary

Much of the knowledge layer already exists in reusable applications. Wikibase supplies identified statements and revisioned entity editing; ResearchSpace supplies contextual narratives and argumentation; VocBench governs vocabularies; Heurist supplies a flexible research workbench. These capabilities can save substantial implementation work. No inspected candidate demonstrates the complete MyBrain journey for preserved originals, versioned meaning, uncertain applications, retained historical results and directly effective access revocation. Candidate roles and extension boundaries therefore matter more than a single product ranking.

## Assessment boundary and evidence

This report corrects an overly broad reading of “the memory layer still needs work”: substantial claim, history, provenance and authoring mechanisms can be reused. Additional work means connecting and governing those mechanisms against MyBrain's contracts. It does not mean inventing a universal knowledge database from scratch.

The earlier [platform report](open-source-platform-candidates.md) investigates ordinary-file services, synchronization, wiki and AI components. This report investigates the knowledge application itself. A file service, a semantic application and an AI index solve different problems, even when one product bundles several functions.

The baseline is [ADR 0001 v1.8](../../architecture/decisions/0001-digital-brain-foundational-principles.md), including P33–P35. Minimal registration, explicit statements and computational representations remain distinct functions. A reusable definition has identity, origin and versioned meaning; applying it to a particular source version is another thing. Uncertainty, dispute and withdrawal about that fit belong to the application. Definition revision remains a separate act. A clear definition can have uncertain applications, and contradictory applications must be able to coexist.

Evidence was checked on **2026-10-24** using official documentation, public repository APIs and released or commit-pinned source. Rolling documentation can describe newer features than a release. Tags, deployment bundles and image versions are distinguished below. No candidate was installed, benchmarked or exercised. All proposed journeys remain unexecuted; code inspection establishes a mechanism, not end-to-end compliance.

Four evidence categories are used: **native** means implemented application behavior; **configured model** means constructing MyBrain objects through existing primitives; **extension** means additional code or an integrating service; **unproven** means the necessary guarantee was not established. Representability in RDF or SQL alone earns no native-feature credit.

## Candidate roles and provisional comparison

These are comparison roles, not four required deployments or an accepted architecture. Source storage preserves originals or explicitly registered references. Authoritative semantic registration records definitions, applications and their histories. Contextual authoring produces narratives and arguments that become new sources. Computational indexes support extraction, comparison and retrieval and may be rebuildable.

| Candidate | Most credible reuse role | Native value | Main remaining burden |
| --- | --- | --- | --- |
| Wikibase / Wikibase Suite | First claim-oriented application candidate | Identified statements, qualifiers, references, revisioned entity editing and APIs. | Explicit definition/source-version binding, temporal applicability, historical retrieval manifests and access enforcement. |
| ResearchSpace | Closest contextual-authoring and argumentation challenger | Narrative interfaces, annotations, attributed beliefs, observations and inferences. | Default ontology adaptation, complete meaning history, preservation and consistent authorization. |
| VocBench / Semantic Turkey | Vocabulary and definition governance specialist | SKOS/OWL/OntoLex editing, validation, triple history, historical resource views and dataset versions. | General source/application model and interface; full required-stack license qualification. |
| Heurist | Flexible structured research workbench | Configurable records, relations, vocabularies, per-value certainty, visualization and record permissions. | Immutable source/definition versions and retrieval evidence; preservation-safe file operations. |
| Semantic MediaWiki / OpenSemanticLab | Semantic wiki and structured authoring | Narrative pages, typed properties/subobjects; OSL adds schema-driven objects/forms. | Explicit claim governance, historical structured states, access limits and OSL distribution licensing. |
| TerminusDB / XTDB | Versioned storage/query engines | Graph commits and branching, or automatic system-time/valid-time history. | Knowledge application, domain semantics, authoring and fine-grained operational rights. |
| Cognee | AI/workbench challenger | Pipelines, connectors, UI/API, lineage machinery and query/completion-text history. | Authoritative definitions/applications, mandatory preservation/provenance completion and release control. |
| Graphiti | Derived semantic extraction/index | Episodes, attributed temporal edges and extraction/retrieval machinery. | Conflict policy, authorization and authoritative source/meaning preservation. |

Wikibase leads for reusable claim registration within this comparison. This is not a recommendation to reproduce Wikidata's interface or to expose every MediaWiki feature. Its API permits a focused front end, but building and maintaining that front end is real work. ResearchSpace merits a direct comparison where the owner primarily works through evolving context and argument. VocBench and Heurist merit specialist trials, not automatic inclusion alongside both leaders. No arbitrary numerical score can resolve these different roles.

## Wikibase: reusable statements before custom claim machinery

Wikibase supplies a real statement model and working editors. Statements carry a main claim, qualifiers, references, rank and a GUID; this is implemented in the [released Statement class](https://github.com/wikimedia/mediawiki-extensions-Wikibase/blob/eaa851d89d36136ab718f1fe5fa81a8b770c0d59/lib/packages/wikibase/data-model/src/Statement/Statement.php). Competing statements can coexist. Qualifiers can express conditions and assessments, while references preserve supplied provenance without certifying truth. Statements without references are admitted by the [official data model](https://www.mediawiki.org/wiki/Wikibase/DataModel), so MyBrain need not impose a rationale document or full inference chain for every application.

A terminology distinction matters: a Wikibase entity's multilingual “label” is its display name. MyBrain's reusable label should be an identified entity with its own definition, origin and versions. Applying that definition to a source version can then be an identified statement, or a separate assignment entity when richer assessment history is needed. These are configured models using native primitives, not a preinstalled MyBrain schema.

Entity revision history and differences are useful. [Revision-specific EntityData](https://www.mediawiki.org/wiki/Wikibase/EntityData/en) can retrieve a particular entity state. A statement referring to definition L does not automatically pin L's definition revision or the recognition/processing contract used. Explicit version objects or equivalent version-bound references remain necessary. A current graph export cannot substitute for those links.

Ranks must not be repurposed casually as truth, confidence or validity. The [full RDF builder](https://github.com/wikimedia/mediawiki-extensions-Wikibase/blob/eaa851d89d36136ab718f1fe5fa81a8b770c0d59/repo/includes/Rdf/FullStatementRdfBuilder.php) preserves statement structure. The [truthy builder](https://github.com/wikimedia/mediawiki-extensions-Wikibase/blob/eaa851d89d36136ab718f1fe5fa81a8b770c0d59/repo/includes/Rdf/TruthyStatementRdfBuilder.php) selects preferred/non-deprecated statements and omits qualifiers and references from the simple predicate view. A convenient truthy query could therefore discard the disputed applicability and temporal qualifications MyBrain needs. Withdrawal requires an explicit assessment/application contract, even if rank assists a current view.

The ordinary synchronized query service is not an archive of every past structured graph. The experimental [Wikidata History Query Service](https://www.wikidata.org/wiki/Wikidata:History_Query_Service) is documented as shut down. Revisioned entities are useful evidence, but recovering every dependency and storing the actual historical delivered result remains additional work.

The [Wikibase API](https://www.mediawiki.org/wiki/Wikibase/API) makes a clean, limited custom interface credible. It also means the full stock wiki interface need not become the owner's everyday experience. The trade-off is an integration layer and front-end maintenance; this is not a free conversion into a small tailored app.

Access is a significant mismatch for private mixed-domain memory. Permissions map principally to pages/entities. A private wiki does not prove that SPARQL, exports and derived processing enforce every source-level restriction. Suite's [pinned reverse-proxy configuration](https://github.com/wmde/wikibase-suite/blob/b4208963b9df586bee979a07e5130c92756f46ee/config/traefik-dynamic.yml) exposes the SPARQL route with read-only controls and rate limiting, without demonstrating per-source authorization. Direct revocation during an unfinished response remains unproven.

The exit route is credible but must be complete: entity JSON/RDF, full-history MediaWiki XML, payloads and [Suite backup/restore](https://github.com/wmde/wikibase-suite/blob/b4208963b9df586bee979a07e5130c92756f46ee/docs/operate/backup-and-restore.md) serve different purposes. Preserve namespaces and identity mappings. Wikibase is the first trial candidate for claim registration, conditional on an acceptable access and preservation boundary.

## ResearchSpace: contextual knowledge and attributed argument

ResearchSpace is the knowledge application at researchspace.org and researchspace/researchspace, distinct from similarly named electronic-lab-notebook and AI products. It is the strongest challenger here when the main activity is creating and exploring context, annotations and arguments. Its [argumentation description](https://researchspace.org/argument/) treats beliefs as attributable to people and times and accommodates different perspectives. Its [semantic tools](https://researchspace.org/semantic-tools/) combine narrative and linked information with annotations, snippets, maps and visualizations.

This has concrete implementation support. At v4.1.0, [ArgumentsApi.ts](https://github.com/researchspace/researchspace/blob/6150c87be1b0a02c7d4c879f807464a7761348f5/src/main/web/components/arguments/ArgumentsApi.ts) gives an assertion its own IRI, target, field, beliefs, note and narrative. Field-based beliefs retain origin repository, target and field; assessments include agreement, disagreement and no opinion. Observations and inferences carry their relevant structures. This is substantially more reusable than a generic promise that RDF can represent claims.

The distinction is promising for source statements, assessments and produced context. It still requires a deliberate MyBrain model for definition versions, applications to A_v1 and an origin link from L to W_v1. A belief assessment is not automatically uncertainty about a label application; those meanings must be specified rather than assumed equivalent.

Native argumentation does not establish immutable meaning history. The inspected assertion path updates an existing assertion IRI. [AbstractLDPContainer](https://github.com/researchspace/researchspace/blob/6150c87be1b0a02c7d4c879f807464a7761348f5/src/main/java/org/researchspace/data/rdf/container/AbstractLDPContainer.java) replaces a resource graph within a transaction. Optional resource persistence records a representation, author and recording time, but that alone does not establish retained earlier versions and their dependent meanings.

There is an important counterbalance: [GitStorage](https://github.com/researchspace/researchspace/blob/6150c87be1b0a02c7d4c879f807464a7761348f5/src/main/java/org/researchspace/services/storage/git/GitStorage.java) supplies revision retrieval for configured platform objects. [MainPlatformStorage](https://github.com/researchspace/researchspace/blob/6150c87be1b0a02c7d4c879f807464a7761348f5/src/main/java/org/researchspace/services/storage/MainPlatformStorage.java) falls back to nonversioned file storage, so neither “everything is versioned” nor “nothing is versioned” is accurate. Configuring versioned platform objects is still different from historic SPARQL graph snapshots and actual retained Q_A output. History must be assessed by object type and deployment configuration.

Adaptation is heavier than a neutral form builder. The current release ships CIDOC-family assumptions and ontology changes; a Java/TypeScript/RDF application and its configuration need competent maintenance. The [released project documentation](https://github.com/researchspace/researchspace/blob/6150c87be1b0a02c7d4c879f807464a7761348f5/README.md) provides an open Blazegraph route, so proprietary GraphDB is not mandatory. Existing [LDP permission checks](https://github.com/researchspace/researchspace/blob/6150c87be1b0a02c7d4c879f807464a7761348f5/src/main/java/org/researchspace/data/rdf/container/PermissionsAwareLDPApi.java) are useful but do not prove atomic revocation over all graph queries and derived disclosures. Trial it against Wikibase for context-centric work, with ontology adaptation and history/access work made explicit.

## VocBench: definition governance with real edit history

VocBench is a multilingual semantic authoring application, not merely a triple store. It supports OWL ontologies, SKOS/SKOS-XL vocabularies, OntoLex lexicons and generic RDF. A MyBrain reusable definition could be a concept or custom resource; a SKOS-XL lexical label is not automatically the same domain object as the owner's reusable description.

Native strengths include role-specific editing, reusable custom forms/views, SPARQL, resource metadata and validation. [History and validation](https://vocbench.uniroma2.it/doc/user/history_and_validation.jsf) track added/removed triples with action metadata in a support repository. Staging separates proposed changes from accepted data; authorized validators accept or reject actions. This is valuable definition governance. Rejecting an editorial change is not the same as retaining a contested application as legitimate historical evidence.

The [Time Machine](https://vocbench.uniroma2.it/doc/user/time_machine.jsf) reconstructs a resource view at prior commits. [Dataset versioning](https://vocbench.uniroma2.it/doc/user/versioning.jsf) can seal immutable dataset versions and fork editable branches; the documentation explicitly limits history/validation on editable forks. These are meaningful native historical facilities. Commit chronology is recording history, however, not a generic rule for when an application was substantively valid. Neither a sealed vocabulary release nor a historic resource view records the actual answer previously delivered.

Automatic metadata patterns can record created/modified information and the acting user. Linking a new definition's origin specifically to W_v1 remains a configured model. Qualified assignment resources, uncertainty, assessment and withdrawal can be modeled and presented with [custom views](https://vocbench.uniroma2.it/doc/user/custom_views.jsf), but that is additional configuration/design rather than native MyBrain behavior.

Recent digital-object annotation support should not be overcredited. The [15.2.0 annotation implementation](https://bitbucket.org/art-uniroma2/semantic-turkey/src/15.2.0/core-services/src/main/java/it/uniroma2/art/semanticturkey/services/core/DigitalObjectAnnotation.java) maintains a Lucene index with an annotation map per digital-object IRI and rejects duplicate registration of that IRI. Its index timestamp does not establish versioned application validity, uncertainty or withdrawal. The RDF history mechanism must not be assumed to cover this separate index.

All functions have Semantic Turkey API seams. The native UI is nevertheless optimized for semantic-resource governance. Rich contextual writing and daily personal knowledge workflows may need another surface or substantial adaptation; original payloads can remain in a separate preservation foundation. The [role/capability model](https://vocbench.uniroma2.it/doc/user/roles_adm.jsf) enforces server-side capabilities per project and operation/resource category; it is not proof of arbitrary per-source disclosure rules or revocation of unreleased results. VocBench is a strong specialist candidate, with the CODA license qualification above, rather than a demonstrated whole-brain application.

## Heurist: flexible records, meaningful history and preservation gaps

Heurist is an existing research data management application. Its configurable record types, pointer fields, relationship records, vocabularies, filtering, maps, timelines, network views and publishing can save substantial interface work. It is oriented to humanities research but need not begin with one fixed domain ontology. Schema flexibility does not establish universal registrability automatically: a minimal source/reference record must remain possible without first understanding the content.

The [GPLv3 source](https://github.com/HeuristNetwork/heurist/blob/948c7a89c40fe003d8ae3677070abc38d96add93/LICENSE_gnuGPL3.txt) includes client and server code. PHP/Apache/MySQL self-hosting is documented; hosted services are an option, not the license basis. Optional external repositories, maps and integrations need separate qualification. The service's current [installation page](https://heuristnetwork.org/Installation) warns that tablets are not fully supported, a material usability constraint for MyBrain.

Heurist's [database schema](https://github.com/HeuristNetwork/heurist/blob/948c7a89c40fe003d8ae3677070abc38d96add93/admin/setup/dbcreate/blankDBStructure.sql) distinguishes vocabulary terms from record field values. Terms have identities, descriptions and originating-database references. Individual data values can carry certainty and an optional annotation; their editing controls can be enabled per field. That directly supports uncertain application without making a term's definition uncertain, although certainty defaults to 1.0 and should not silently mean an independently established fact. The existing enum term ID does not itself pin the historical definition version.

History is more than a log of who clicked. [Database triggers](https://github.com/HeuristNetwork/heurist/blob/948c7a89c40fe003d8ae3677070abc38d96add93/admin/setup/dbcreate/addProceduresTriggers.sql) preserve previous record/detail values on updates and deletions. [DbSysArchive](https://github.com/HeuristNetwork/heurist/blob/948c7a89c40fe003d8ae3677070abc38d96add93/hserv/entity/DbSysArchive.php) exposes field history and restoration. However, its reconstruction consults current structure; inspected term triggers maintain hierarchy rather than recording the same version history. Complete historical interpretation across changing vocabularies/structures was not established.

Original-byte preservation is a concrete gap. [DbRecUploadedFiles::replaceLocalFiles](https://github.com/HeuristNetwork/heurist/blob/948c7a89c40fe003d8ae3677070abc38d96add93/hserv/entity/DbRecUploadedFiles.php) updates an existing file identity and can delete the former physical path. Field history is not a substitute for the deleted bytes. MyBrain would need a safe immutable-version route or an external authoritative source store.

Record/workgroup permissions are real application features, described in the [administration tutorial](https://heuristnetwork.org/10690). They do not prove the same policy over history, files, exports and running retrievals. The schema also distinguishes hiding a value from public display from using it in filtering/analysis: display hiding must not be mistaken for authorization. Heurist deserves a structured-workbench trial, particularly for low-code record editing, but preserved definition versions, source-version assignment records and retained query evidence remain additional work.

## Semantic MediaWiki and OpenSemanticLab: structured wiki alternatives

Semantic MediaWiki combines familiar narrative pages with typed properties and queries. [Subobjects](https://www.semantic-mediawiki.org/wiki/Help:Subobjects) can group an assignment's source-version link, definition-version link, uncertainty and conditions. Named subobjects or dedicated pages can provide deliberate identities. That is a configured application model; an ordinary annotation is not inherently an independently governed claim.

The decisive history boundary is the [associated revision](https://www.semantic-mediawiki.org/wiki/Help:Associated_revision). The semantic store tracks the page revision used to build its current structured representation, while subobjects have no independent associated revision. Old page text remains valuable, but current semantic queries do not automatically query the whole historical structured graph. Released [7.3.1 update code](https://github.com/SemanticMediaWiki/SemanticMediaWiki/blob/7.3.1/src/SQLStore/SQLStoreUpdater.php) updates property rows and removes unreferenced subobjects. Its query cache is a performance mechanism, not a retained delivered-result record.

OpenSemanticLab deserves serious adjacent consideration: MwJson provides schema-driven forms, structured slots, JSON-LD and integration with Python tooling. This can save work that a bare semantic wiki would leave to developers. [Current MwJson documentation](https://github.com/OpenSemanticLab/mediawiki-extensions-MwJson/blob/26837787318222ed8dafb949c3ff0ee2e2db9e8c/README.md) describes revision-aware reads and approved-revision integration. Selecting an approved active revision still does not preserve all historical query states.

The [v2.2.2 composition](https://github.com/OpenSemanticLab/docker-compose-osl-wiki/blob/v2.2.2/docker-compose.yml) selects Elasticsearch 7.10.2's default distribution. Its [actual license](https://github.com/elastic/elasticsearch/blob/v7.10.2/LICENSE.txt) distinguishes that binary from the Apache-licensed OSS build. The shipped stack therefore cannot receive unqualified fully-open-source status; a compatible replacement route remains untested. The sampled [compose license](https://github.com/OpenSemanticLab/docker-compose-osl-wiki/blob/v2.2.2/LICENSE), [MwJson manifest](https://github.com/OpenSemanticLab/mediawiki-extensions-MwJson/blob/26837787318222ed8dafb949c3ff0ee2e2db9e8c/extension.json) and [osw-python metadata](https://github.com/OpenSemanticLab/osw-python/blob/v2.8.2/pyproject.toml) declare Apache-2.0 despite stale AGPL descriptions. This does not change MediaWiki/SMW's own licenses. The [released Dockerfile](https://github.com/OpenSemanticLab/docker-compose-osl-wiki/blob/v2.2.2/mediawiki/build/Dockerfile) clones moving extension branches; separately inspected MwJson/osw versions are not a verified immutable extension set shipped by the compose tag.

OSL includes SemanticACL, but the [inspected implementation](https://github.com/OpenSemanticLab/mediawiki-extensions-SemanticACL/blob/37e1118bbe19db7a301a3632df069f296d55800d/SemanticACL.class.php) does not filter count queries and caches decisions during a request. These are material boundaries for access-respecting completeness and immediate revocation. They do not establish an exploit or imply every configured file route leaks. SMW/OSL remain useful authoring alternatives, with a larger claim/history gap than Wikibase and concrete distribution qualifications.

## TerminusDB and XTDB: reuse temporal engines without mistaking them for applications

TerminusDB's [12.0.8 release](https://github.com/terminusdb/terminusdb/releases/tag/v12.0.8) is an actively maintained Apache-2.0 graph/document engine. It supplies schema enforcement, immutable commits, branching, merging, diffs and commit-specific queries. Modeling source registrations, definitions, applications and contracts as documents could reuse this revision machinery rather than rebuilding it. Its v12 [interval tests](https://github.com/terminusdb/terminusdb/blob/v12.0.8/tests/test/document-interval.js) demonstrate interval datatypes; the [released feature description](https://github.com/terminusdb/terminusdb/blob/v12.0.8/README.md) separately describes temporal reasoning. These go beyond recording snapshots, but neither source demonstrates MyBrain's application-validity contract.

Intervals still need domain meaning: which application applies during the interval, who assessed it, and whether another interpretation remains contested. A schema version is not automatically the owner's reusable definition version. A commit can preserve contradictory claim documents without deciding which is true, provided the application model and selection contract retain both.

A commit-specific query gives a strong database basis, not evidence that Q_A actually ran or that its exact output was delivered. Released [capabilities](https://github.com/terminusdb/terminusdb/blob/v12.0.8/src/core/account/capabilities.pl) govern organizations/databases and distinguish instance, schema, metadata and commit operations. Arbitrary source-level policy and running-result revocation were not established. The released dashboard is a [discontinuation notice](https://github.com/terminusdb/terminusdb/blob/v12.0.8/dashboard/src/index.html); rolling descriptions of a newer admin console should not be credited as a shipped complete knowledge UI. Enterprise-only facilities need separate treatment.

XTDB [2.2.0](https://github.com/xtdb/xtdb/releases/tag/v2.2.0) is an MPL-2.0 engine with automatic system-time and valid-time history. This directly reduces work for late arrivals and retrospective corrections: what was recorded at one time about applicability at another time can be queried separately. It supplies a stronger temporal default than manually adding a modified timestamp.

XTDB's [query-basis documentation](https://docs.xtdb.com/about/txs-in-xtdb.html) recommends preserving both SNAPSHOT_TOKEN and CLOCK_TIME for full repeatability. That is valuable Q_A infrastructure, while the actual result, contracts and external processing configuration must still be retained. Neither engine supplies MyBrain's definition/application authoring interface. XTDB authentication also must not be mistaken for completed object-level GRANT/REVOKE support; the [object-rights issue](https://github.com/xtdb/xtdb/issues/5687) remains open in the inspected project state. These are serious alternative engine trials after the application boundary is clear, not extra mandatory products.

Current Fluree 4.2.4 is excluded from the strict open-source shortlist because its [actual license](https://github.com/fluree/db/blob/v4.2.4/LICENSE) is BUSL-1.1 and explicitly distinguishes itself from an open-source license. A future Apache conversion or permissive internal-use allowance does not qualify today's release. Older versions would need a separate exact-version assessment.

## Cognee and Graphiti: computational reuse with different authority limits

Cognee is the stronger AI/workbench challenger here. The [1.6.5 baseline](https://github.com/topoteretes/cognee/releases/tag/v1.6.5) includes UI/API/CLI components and pipeline machinery, and its [provenance manager](https://github.com/topoteretes/cognee/blob/v1.6.5/cognee/modules/provenance/manager.py) implements version archival, predecessor links, lineage, validity fields, attributed activities and integrity/history facilities. This deserves positive credit beyond “graph plus vectors.”

The guarantee is configuration-dependent. Its [provenance task](https://github.com/topoteretes/cognee/blob/v1.6.5/cognee/tasks/provenance/record_provenance.py) makes ledger tracking opt-in, separate from lightweight provenance stamping, and allows ingestion to continue after provenance failures. MyBrain would need a completion/failure contract so successful ingestion cannot silently mean complete provenance. This is an extension to operational policy, not necessarily a replacement provenance engine.

Cognee's [search-history logger](https://github.com/topoteretes/cognee/blob/v1.6.5/cognee/modules/search/operations/log_search_history.py) records queries and completion/context text by default when exposed by a result payload. Other result types can be logged as empty text. This helps retain some historical outputs; full actual-result preservation still needs a response-type contract. The logger does not establish a manifest of exact source, definition, assignment, contract and model versions. Its [temporal retriever](https://github.com/topoteretes/cognee/blob/v1.6.5/cognee/modules/retrieval/temporal_hybrid_retriever.py) reranks using time anchors and can fall back to ordinary hybrid retrieval; this is different from historical database-state querying.

The [update path](https://github.com/topoteretes/cognee/blob/v1.6.5/cognee/api/v1/update/update.py) preserves a data identity while updating/rebuilding derived memory. It does not establish immutable histories of every original and representation. Dataset ACLs are useful but do not prove atomic revocation during generation. An eligible local route uses [Ladybug 0.19.0 under MIT](https://github.com/LadybugDB/ladybug/blob/v0.19.0/LICENSE), [LanceDB 0.39.0 under Apache-2.0](https://github.com/lancedb/lancedb/blob/v0.39.0/LICENSE) and open relational components, subject to model licenses. The [released Cognee documentation](https://github.com/topoteretes/cognee/blob/v1.6.5/README.md) distinguishes the open all-Postgres graph demo from a separately licensed production product; the demo must not receive production credit. Cognee 1.6.6rc1 is named as a release candidate despite inconsistent API prerelease metadata, so this assessment uses 1.6.5.

Graphiti [0.31.2](https://github.com/getzep/graphiti/releases/tag/v0.31.2) supplies temporal extraction/retrieval infrastructure. Its [edge model](https://github.com/getzep/graphiti/blob/v0.31.2/graphiti_core/edges.py) distinguishes creation, validity, invalidation and expiration times and links facts to episodes. These mechanisms can reduce extraction and lineage work.

However, its [contradiction-resolution path](https://github.com/getzep/graphiti/blob/v0.31.2/graphiti_core/utils/maintenance/edge_operations.py) automatically expires overlapping older contradictory edges while retaining them. That is an implemented supersession policy. MyBrain requires competing applications to remain available without a later incompatible statement automatically making the earlier one inapplicable. Inference: Graphiti fits most safely as a replaceable derived index unless this policy is controlled or adapted. Custom type definitions do not themselves create versioned reusable label items.

The [released server boundary](https://github.com/getzep/graphiti/blob/v0.31.2/README.md) explicitly states that reference MCP/REST servers lack authentication and authorization: group_id is not an ACL. An authorized service is required for production. [Neo4j Community](https://github.com/neo4j/neo4j/blob/5.26.0/LICENSE.txt) offers an eligible GPLv3 route; promoted [FalkorDB's inspected license](https://github.com/FalkorDB/FalkorDB/blob/master/LICENSE.txt) is SSPL and fails this strict gate. That FalkorDB observation uses rolling master, not a release-pinned dependency audit. Neither a managed Zep product nor Enterprise Neo4j rights should be credited to the open framework. All extraction/model configurations still need versioned processing records.

## What history means in this comparison

| Mechanism | What it establishes | What it does not establish alone |
| --- | --- | --- |
| Edit audit or revision | Who changed a recorded object and which state was retained. | When its meaning or application was substantively valid. |
| Valid-time representation | An explicitly interpreted applicability period. | That the assertion is true, or that a later assertion supersedes it. |
| Historic database/query basis | Which recorded graph/records a query can inspect. | That an earlier execution occurred or what was actually delivered. |
| Saved query | A reusable selection expression. | An immutable result or the exact historical processing basis. |
| Retained answer/result | What a particular execution produced. | Complete provenance, coverage, authorization or reproducibility without its manifest. |
| Versioned processing context | Model, extraction/retrieval configuration and contract versions used. | Replay of opaque model internals or proof every relevant cause was captured. |

Wikibase revisions, VocBench's Time Machine, Heurist's field archive, configured ResearchSpace Git storage, TerminusDB commits, XTDB temporal queries and Cognee's completion-text logger are useful but different mechanisms. None should be flattened into a generic “supports history” checkbox. A later current query is not a reconstruction of an earlier actual result.

Likewise, registering a digital contract does not activate or enforce it. Stored source properties may inform comparison eligibility, while the operational contract layer evaluates and governs processing. Retrieval authorization is a distinct obligation alongside stored information. A schema or ontology cannot by itself cancel disclosure from a running request.

## One synthetic acceptance journey for application trials

The following is a proposed test contract, not an implementation plan or executed evidence. Use entirely synthetic sources and identities. Begin with Wikibase and ResearchSpace for the application comparison; include a specialist or engine only when a specific gap makes its contribution testable.

| Step | Synthetic action | Required observable result |
| --- | --- | --- |
| Register source A_v1 | Admit a binary or digital record with minimal factual registration; also register an unsupported/encrypted item by an authorized reference. | Identity, origin claims, receipt and preservation/reference guarantees remain distinct. Lack of semantic understanding does not block registration. A stored reference does not claim its target bytes are preserved. |
| Produce W_v1 | Create and save context derived from A_v1 through the candidate's authoring surface. | W_v1 is an independently addressable source with its own version and explicit derivation basis. It can be selected and described like other sources. |
| Create L and L_v1 | Define a reusable label with origin W_v1; later reuse it elsewhere. | Reuse preserves origin. Identity/display name, definition version and origin context are distinguishable; no duplicate rationale or full inference chain is universally demanded on every use. |
| Apply L_v1 uncertainly | Create application AP1 to A_v1; retain a conflicting source statement or alternative application. | Uncertainty belongs to AP1. L_v1 need not change. Attribution and the applicable contract can be recovered without silently selecting one application as truth. |
| Record Q_A | Run a controlled selection and return context/content under an explicit response contract. | Retain actual result plus source/definition/application states, retrieval/processing contract versions, method, model/configuration and scope actually used. Selection basis and disclosed response need not contain the same descriptions. |
| Change meaning/use | Withdraw or narrow AP1, then revise L separately only if its definition changes; introduce A_v2. | Earlier source and definition versions, assessment changes and prior use remain accessible within rights. Record time and effective validity remain distinct; the newest version does not silently win every interpretation. |
| Record Q_B | Run the current-applicability query after these changes. | Q_B may differ; Q_A's actual result and original basis remain recoverable. Historical use does not silently become a fresh current assessment. |
| Preserve correction | Let an automated reprocessing job encounter an owner correction. | The correction and its history remain effective under their scope; automation does not silently overwrite them. |
| Revoke during execution | Pause after retrieval but before releasing part of a result; revoke the relevant right and resume. | From the declared effective point, no additional information is disclosed under that right, including unreleased derived context. The change is atomic within its scope. Already delivered copies cannot be recalled. |
| Restore and replace | Export/back up, restore elsewhere, then rebuild an index or change the model. | Stable identities, preserved versions, definitions/applications, rights, processing manifests and Q_A evidence survive; rebuilding a current index does not masquerade as restoring historic outputs. |
| Inspect incomplete work | Fail an extractor, delay an index update and query an unsupported item. | Intake, processing and retrieval completeness are assessed separately against explicit scopes. Empty search does not prove nonexistence or disclose inaccessible existence. |
| Exercise explicit destruction | In a separate fixture, let only the authorized owner choose a destruction scope. | Withdrawal/hiding never triggers destruction by itself. Demonstrate the chosen boundary across versions, derivatives and backups and the remaining traceability limits. |

Evaluate the interface too: a clean route for registering a definition, applying it uncertainly, reviewing competing applications and retrieving earlier context should not require exposing unrelated administration features. APIs make tailored interfaces possible but do not eliminate adaptation cost. Lack of workstation synchronization is not a knowledge-application failure; the earlier platform comparison owns that concern. Preserved source-version links and compatible integration with a separate source foundation are the relevant knowledge boundary.

## Provisional reuse strategy and remaining decision

The strongest first comparison is **Wikibase for identified claim registration versus ResearchSpace for context and argument authoring**. Their differences concern daily authoring and the cost of preserving meaning, not whether either can store arbitrary graph nodes. Retain Cognee as a serious AI/workbench challenger where its pipelines, lineage and query/completion-text history can remove integration work.

VocBench can supply vocabulary governance if a dedicated editor is useful and its full dependency-license qualification is resolved. Heurist offers flexible record editing and analysis with relatively accessible configuration, provided source preservation and versioned definitions are explicit. SMW/OSL are adjacent authoring options; OSL's default composition needs a verified open replacement before advancing under the strict gate. TerminusDB and XTDB remain alternative engine references, not additional mandatory installations. Graphiti is most credible as computational infrastructure with controlled conflict behavior.

This is a research inference and a proposed trial order, not adoption of MediaWiki, CIDOC, RDF, SQL, a base ontology or a multi-product architecture. Knowledge applications need not replace the file foundation. Their attachment operations matter when used to keep originals; otherwise the trial should test durable source-version references to the separately preserved material.

The major unresolved decisions are authoritative object/version modeling, usable authoring, complete export/restore, historical dependency and result capture, contract activation, and authorization over every disclosure path. Required-stack license checks must be repeated for the actual pinned deployment, including models. The [Open Source Definition](https://opensource.org/osd) and [Creative Commons software-license guidance](https://creativecommons.org/faq/#can-i-apply-a-creative-commons-license-to-software) explain why source availability and CC licensing deserve careful qualification; this screening criterion does not add a new owner architecture decision.

No acceptance journey has been executed. No original mail or NAS ingestion is resumed, and no application stack or implementation approval follows from this report.
