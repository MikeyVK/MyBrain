# Open source platform candidates for MyBrain

**Status:** Research assessment  
**Version:** 1.0  
**Last Updated:** 2026-10-24

## Purpose

Identify the most compatible open-source foundation for further MyBrain evaluation, while preserving the distinction between an integrated workspace, storage, knowledge processing and authoritative memory.

## Summary

Nextcloud leads the integrated-platform shortlist; OpenCloud is the storage-focused alternative. AnythingLLM and an open-source wiki can be evaluated as optional components. No examined candidate demonstrates all MyBrain guarantees without additional integration and validation. This is a research recommendation, not an adoption decision.

## Executive assessment

**Nextcloud is the strongest integrated platform to prototype as a file and workspace foundation. OpenCloud is the strongest storage-focused alternative. AnythingLLM is the leading optional AI component in this shortlist; SilverBullet's MIT server is a possible wiki component.** These are role-specific recommendations, not interchangeable winners or an approved stack.

The examined projects reuse substantial functionality already needed by MyBrain: ordinary local files, synchronization, cross-device access, document interfaces, retrieval and AI orchestration. No examined candidate has demonstrated the complete combination of historical source and description identities, evolving contracts, label origins and assignment validity, reproducible historical query evidence, and atomic prospective revocation across retrieval and generated results. That is a bounded finding from this investigation, not a claim that no such project can exist.

The proposed next decision is which small, synthetic comparison to authorize. A platform installation or a source-code fork is not justified merely by this report. Reusing public extension interfaces is preferable to assuming a wholesale rewrite, while the strongest guarantees need their own explicit contracts and evidence.

Nextcloud offers the broadest integrated starting position, but stock Context Chat is a current-state index with asynchronous access updates. OpenCloud offers an attractive file-oriented boundary with less integrated knowledge functionality. Their respective gaps suggest preserving the distinction between the workspace, the authoritative memory, and replaceable processing or search components.

Commercial support is not itself a disqualification. The relevant license question is whether the components required for a proposed capability are genuinely open source. Optional paid applications, source-available features, model weights and hosted services must each be checked separately.

## Evaluation basis and limits

The accepted reference is [ADR 0001, version 1.8](../../architecture/decisions/0001-digital-brain-foundational-principles.md), together with the [discussion map](../../architecture/digital-brain-discussion-map.md). Later scenario requirements from the owner's discussion are used here as research criteria; this document does not silently amend those principles.

| Criterion | What a candidate must support or leave possible |
| --- | --- |
| General registration | Digitally recordable items, including original content, descriptions, produced context and contracts, without requiring prior semantic understanding. |
| Separation of responsibilities | Knowledge and descriptions are independent of physical payload location; stored contract artifacts remain distinct from operational evaluation and enforcement. |
| Ordinary offline work | Important workstations can edit actual local files in native applications while disconnected. Browser caches and virtual placeholders are different capabilities. |
| New-device access | Compatible content can be presented, and originals retrieved for native use. A web interface is plausible, not an adopted requirement for every function. |
| Change lifecycle | Changed, recognized, registered and processed states remain distinguishable for the relevant source version. |
| Preservation and identity | Required registered versions and historical descriptions remain traceable. A preserved pointer alone is not preservation of its target. |
| Meaning and query history | Definition, origin, assignment, applicability and historical use do not collapse into a mutable tag or current vector index. |
| Owner control | Preservation is standard; destruction requires the owner's explicit choice. Rights and prospective revocation must cover unreleased information in the declared scope. |
| Practical extensibility | Public APIs, events and providers make a bounded extension credible without assuming every desired semantic guarantee is already implemented. |

The offline requirement concerns actual available copies. Revoking central rights cannot recall information already delivered to a workstation or recipient. The open question is prospective disclosure by the controlled system, including running retrieval and generation, rather than retroactively erasing previously delivered knowledge.

Evidence distinguishes documented functionality, inspected source behavior, configuration choices and remaining uncertainty. Released tags or commit references are used for sensitive findings; floating documentation is dated to this review, **2026-10-24**. No candidate was installed, exercised with private data or security-tested. Published hardware numbers and UI features are not benchmark results.

Licensing observations concern the named components and paths, not an exhaustive dependency audit or legal opinion. Project popularity, stars, a recent release, and the existence of a repository are not proof of correctness, durability or authorization guarantees.

## Nextcloud: the strongest integrated starting point

Nextcloud's advantage is the existing user journey around files. Its desktop client synchronizes an ordinary local directory, allowing native applications to use hydrated files offline. This is a practical match for a digital brain whose knowledge layer must not dictate every editing application. Virtual files still need hydration; a placeholder is not an offline original. [Desktop client documentation](https://docs.nextcloud.com/server/stable/user_manual/en/desktop/usage.html) describes that distinction. The [web interface](https://docs.nextcloud.com/server/stable/user_manual/en/files/access_webgui.html) provides previews, navigation and downloads, giving a useful new-device route without converting every format into wiki text. Actual preview coverage and mobile edit-and-return behavior remain acceptance-test questions.

A conflict is already a meaningful boundary between preservation on a device and registration in the brain. Nextcloud documents downloading the remote file while keeping a local conflicted copy; uploading conflict files is not the default. Consequently, a user's locally preserved edit cannot automatically be counted as centrally captured or processed. The integration must surface that state instead of treating a successful sync of other files as proof of complete capture. [Documented conflict behavior](https://docs.nextcloud.com/server/stable/user_manual/en/desktop/conflicts.html)

Storage topology also matters. With primary object storage, the bucket contains objects identified by IDs while names and directory structure are held in the database. This is different from an independently readable ordinary server folder. It is a supported design, but restore and exit procedures must preserve the database/content relationship. [Primary storage documentation](https://docs.nextcloud.com/server/stable/admin_manual/configuration_files/primary_storage.html) Ordinary local desktop files do not imply that every supported server backend has the same property.

External storage offers a bridge to existing locations, but it introduces another observation boundary. Changes made outside Nextcloud may require scanning or backend notifications. The official documentation warns that an external rename can appear as deletion plus creation and lose associated shares, tags, comments or activity. A supported mount therefore does not by itself prove stable identity under every editing route. The appropriate route is to test Nextcloud-mediated operations and each proposed external-write mechanism separately. [External storage change and rename limitations](https://docs.nextcloud.com/server/stable/admin_manual/configuration_files/external_storage_configuration_gui.html)

**Preservation requires configuration and an explicit registration boundary.** Default version expiration is unsuitable as evidence for owner-only destruction. Nextcloud documents retention controls, and inspected NC35.0.2 code recognizes the `disabled` retention setting. That can protect created versions from automatic expiration; it does not prove every intended source version was created or independently registered. [Retention configuration](https://docs.nextcloud.com/server/stable/admin_manual/configuration_files/file_versioning.html), [released expiration implementation](https://github.com/nextcloud/server/blob/ba900af933e61ffa005315b09d6454bfbbcbcc81/apps/files_versions/lib/Expiration.php)

There is a material unresolved capture detail. User documentation describes a two-minute version interval, while the inspected storage path did not establish a matching universal guard; the legacy backend uses modification time in version filenames. This documentation/code discrepancy needs a targeted test, including rapid saves and timestamps, rather than an assertion that all edits are preserved or that a particular cadence certainly applies. The criterion is preservation of agreed registered versions, not every keystroke. [Version-control user documentation](https://docs.nextcloud.com/server/stable/user_manual/en/files/version_control.html), [pinned legacy version backend](https://github.com/nextcloud/server/blob/ba900af933e61ffa005315b09d6454bfbbcbcc81/apps/files_versions/lib/Versions/LegacyVersionsBackend.php)

**The extension surface is promising.** WebDAV provides a supported file boundary; metadata APIs can attach typed file metadata, and application events allow reactions to changes. These are credible places to connect a registration service without directly rewriting core database tables. Their existence does not establish an append-only description history, durable exactly-once event delivery or the meaning of an observed update. Those semantics would belong to the extension contract. [WebDAV API](https://docs.nextcloud.com/server/stable/developer_manual/client_apis/WebDAV/basic.html), [file metadata API](https://docs.nextcloud.com/server/stable/developer_manual/digging_deeper/files-metadata.html), [event extension documentation](https://docs.nextcloud.com/server/stable/developer_manual/basics/events.html)

Nextcloud's Context Chat provider interface can also submit non-file application content with provider/source IDs, text, modification information and allowed users. That is an extension seam for more than a file folder, while preserving the distinction between submitted index content and authoritative original registration. [Content provider interface](https://docs.nextcloud.com/server/stable/developer_manual/digging_deeper/context_chat.html)

Assistant and Context Chat add a useful integrated retrieval experiment. The documented backend requires its own deployment and a text-generation provider; local and remote provider choices are possible. Published resource requirements include CPU instruction support and substantial memory, so an arbitrary existing host cannot be assumed suitable. Provider and model licensing must be evaluated independently of the application's open-source license. [Context Chat administration requirements](https://docs.nextcloud.com/server/stable/admin_manual/ai/app_context_chat.html), [AI provider overview](https://docs.nextcloud.com/server/stable/admin_manual/ai/overview.html)

**Stock Context Chat should be treated as a replaceable current-state index.** In the pinned v5.5.0 backend, source IDs identify stored documents; a newer modification time can remove earlier indexed chunks and replace them. That supports keeping search current, not retaining a historical index for every registered source version. The search path filters by the backend's access lists, but that is a different guarantee from rechecking every prospective disclosure against the current authoritative right. [pinned vector-store implementation](https://github.com/nextcloud/context_chat_backend/blob/15c9f30e457475387023256ea5f37f0ee1f93c2a/context_chat_backend/vectordb/pgvector.py)

The PHP adapter excludes version and trash directories from the ordinary file-indexing path. Its queue handoff carries a file source ID, modification time, type and size, rather than an immutable source-version identity. Citation links resolve through current file IDs and names. These are useful navigable references, but they cannot alone prove which historical bytes supported an earlier answer. [file eligibility implementation](https://github.com/nextcloud/context_chat/blob/99771473f16b81dbafe7d7962fdc62ad1e753b46/lib/Service/FsEventService.php), [queue handoff](https://github.com/nextcloud/context_chat/blob/99771473f16b81dbafe7d7962fdc62ad1e753b46/lib/Controller/QueueController.php), [citation metadata implementation](https://github.com/nextcloud/context_chat/blob/99771473f16b81dbafe7d7962fdc62ad1e753b46/lib/Service/MetadataService.php)

**Access control is the decisive limitation.** Context Chat explicitly documents that rules from the separate Files Access Control application are not followed in its retrieval path. Access changes are also propagated through scheduled backend actions. The pinned scheduler confirms queued access updates. This is incompatible with assuming MyBrain's direct, atomic prospective revocation requirement is already satisfied, especially during a running generation. It is a documented integration boundary, not a tested exploit or a claim that every Nextcloud file API ignores permissions. [documented access-control limitation](https://docs.nextcloud.com/server/stable/admin_manual/ai/app_context_chat.html), [scheduled access-update code](https://github.com/nextcloud/context_chat/blob/99771473f16b81dbafe7d7962fdc62ad1e753b46/lib/Service/ActionScheduler.php)

Recovery must cover originals, database state, configuration and added processing stores. Nextcloud's documented backup set is a starting point; historical registration and query evidence introduced by MyBrain would need their own coordinated recovery boundary. Context Chat's documented embedding-model replacement involves resetting derivative index state, which must not be confused with destruction of original files. [Nextcloud backup documentation](https://docs.nextcloud.com/server/stable/admin_manual/maintenance/backup.html), [embedding-model migration procedure](https://docs.nextcloud.com/server/stable/admin_manual/ai/app_context_chat.html)

Finally, server-side indexing needs readable content. End-to-end encryption, where the server cannot read plaintext, changes what that server can process; a trusted client-side decryption/indexing route would be a separate design. This inference follows from the [documented encryption boundary](https://nextcloud.com/encryption/). Nextcloud remains the leading integrated candidate because it minimizes routine workspace construction, while leaving the memory and authorization guarantees visible as additional work.

## OpenCloud: the strongest storage-focused alternative

OpenCloud deserves a direct comparison rather than being treated as an inferior Nextcloud clone. Its attraction is a smaller conceptual distance between a file service and independently accessible storage. Desktop synchronization and web/mobile file access address the everyday workflow, while its POSIX backend keeps readable files with extended attributes. These properties fit a framework in which physical storage and knowledge descriptions remain separate. [Desktop workflow](https://docs.opencloud.eu/docs/user/desktop-client/), [file interfaces](https://docs.opencloud.eu/docs/user/files-and-folders/), [POSIX storage design](https://docs.opencloud.eu/de/docs/admin/configuration/storage/storage-posix/)

That openness does not mean arbitrary direct filesystem changes are automatically safe. The documented collaborative mode imposes constraints on operations such as links, movement between Spaces and large change sets, and may bypass checks normally attached to uploads. In both inspected v7.2.4 and v8.1.0 defaults, filesystem watching and filesystem revision creation are disabled. Upload versioning and versions created from external filesystem changes are therefore distinct capabilities. A deployment relying on external editors must deliberately establish its supported change route. [production defaults](https://github.com/opencloud-eu/opencloud/blob/v7.2.4/services/storage-users/pkg/config/defaults/defaultconfig.go), [rolling defaults](https://github.com/opencloud-eu/opencloud/blob/v8.1.0/services/storage-users/pkg/config/defaults/defaultconfig.go)

The important comparison is not simply “database versus files.” Nextcloud can synchronize ordinary desktop files, and OpenCloud still maintains service metadata and access state. OpenCloud's POSIX design is attractive for portability, but recovery must preserve content together with relevant metadata, identities and service configuration. A copied directory without its identity information is not automatically a faithful reconstruction of a knowledge history. This is a design inference to validate, not a demonstrated recovery result.

Public WebDAV IDs and ETags support an adapter that recognizes and retrieves files. Server-sent events can improve responsiveness, and the web extension system supplies views, actions and sidebar integrations. These are useful seams for MyBrain's descriptions and processing states. They do not establish a durable event ledger or historical label/application contracts merely by existing. [WebDAV API](https://docs.opencloud.eu/docs/dev/server/apis/http/webdav/), [server-sent events](https://docs.opencloud.eu/docs/dev/server/services/sse/information/), [web extension system](https://docs.opencloud.eu/docs/dev/web/extension-system/)

Access revocation needs explicit testing here as well. The pinned proxy code caches external identity-provider group synchronization for five minutes, and the OIDC path can reuse claims until token expiry. These findings concern particular identity-provider routes; they do not imply every local share change is delayed by five minutes. They do prevent a blanket claim that all authorization changes immediately govern every in-flight use. [group-membership synchronization cache](https://github.com/opencloud-eu/opencloud/blob/v7.2.4/services/proxy/pkg/middleware/account_resolver.go), [OIDC claim-cache implementation](https://github.com/opencloud-eu/opencloud/blob/v7.2.4/services/proxy/pkg/middleware/oidc_auth.go)

The core examined components have open-source licenses: Apache-2.0 server, AGPLv3 web, GPLv2 desktop, GPLv3 iOS and GPLv2 Android. The client licenses were inspected separately; this is not a complete dependency audit. Commercial long-term maintenance and subscriptions must be distinguished from source availability. Production and rolling tracks also require separate operational decisions. [Server license](https://github.com/opencloud-eu/opencloud/blob/v7.2.4/LICENSE), [web](https://github.com/opencloud-eu/web/blob/main/LICENSE), [desktop](https://github.com/opencloud-eu/desktop/blob/main/COPYING), [iOS](https://github.com/opencloud-eu/ios/blob/main/LICENSE), [Android](https://github.com/opencloud-eu/android/blob/main/LICENSE.txt), [release lifecycle](https://docs.opencloud.eu/docs/admin/resources/lifecycle/)

My recommendation is to retain OpenCloud as the storage challenger in a small comparison. It could win if transparent file storage and a narrower platform boundary matter more than integrated Assistant workflows. It currently offers less evidence of an integrated knowledge/AI journey, so that route would assemble more components. Neither a simpler storage design nor open licensing removes the need for explicit preservation, provenance and release-time authorization contracts.

## AI components: AnythingLLM and Khoj

**AnythingLLM is the first optional AI component to evaluate.** The inspected v1.18.0 release has an MIT license and exposes APIs for document, embedding and chat workflows. Its self-hosting terms describe local storage and operation with local model/vector providers; air-gapped operation requires deliberately choosing that complete route rather than assuming any provider configuration remains local. [Released license](https://github.com/Mintplex-Labs/anything-llm/blob/v1.18.0/LICENSE), [developer API](https://docs.anythingllm.com/features/api), [self-hosting terms](https://github.com/Mintplex-Labs/anything-llm/blob/v1.18.0/TERMS_SELF_HOSTED.md)

Its internal document storage is parsed content alongside application and vector state. That is useful for retrieval, but it is not evidence that every original binary is preserved. The documented live-document synchronization feature is experimental and limited: desktop local uploads, individual files rather than folders, and no move tracking. Browser-uploaded Docker documents do not become a workstation file watcher. [Storage layout](https://docs.anythingllm.com/installation-desktop/storage), [live document sync limits](https://docs.anythingllm.com/beta-preview/active-features/live-document-sync)

The pinned watcher compares content and replaces outdated vectors when changes are detected. This helps distinguish unchanged inputs from updated processing, but it does not create immutable source histories or historical embeddings. Its success/failure tracking is useful implementation material, not proof of completeness over all intended sources. An AnythingLLM integration should consume explicitly registered versions from a source service and return artifacts with traceable identities. [Released synchronization job](https://github.com/Mintplex-Labs/anything-llm/blob/v1.18.0/server/jobs/sync-watched-documents.js)

**Khoj remains a credible alternative personal assistant.** Its AGPL-licensed self-hosted path and local-model documentation suit sovereignty goals. However, its desktop connector sends configured local file content into an index; it is not a bidirectional file-hosting service. The inspected desktop code checks folders and modification times, uploads content and removes vanished files from the index. [License](https://github.com/khoj-ai/khoj/blob/master/LICENSE), [desktop client role](https://docs.khoj.dev/clients/desktop/), [inspected connector](https://github.com/khoj-ai/khoj/blob/ae229ca894c0b80ad84664afcfdde523b5e87057/src/interface/desktop/main.js), [local model setup](https://docs.khoj.dev/advanced/ollama/)

The inspected processor updates extracted text and replaces old fragments. Citations and file hashes are valuable, but that behavior does not prove immutable original-binary or description history. Khoj Cloud was deprecated on 2026-04-15 according to the checked source banner; self-hosting continues, and repository activity should not be misrepresented as abandonment. The latest examined release is still a March beta. [processor implementation](https://github.com/khoj-ai/khoj/blob/ae229ca894c0b80ad84664afcfdde523b5e87057/src/khoj/processor/content/text_to_entries.py), [cloud deprecation notice](https://github.com/khoj-ai/khoj/blob/ae229ca894c0b80ad84664afcfdde523b5e87057/src/interface/web/app/components/deprecationBanner.tsx), [release baseline](https://github.com/khoj-ai/khoj/releases/tag/2.0.0-beta.28)

The preference for AnythingLLM is therefore conditional: a clearer current release baseline and a bounded AI-component role, not proof that its answers or security are better. Both candidates require evaluation of source-version citations, explicit processing states, access boundaries and model/provider licenses. Neither should become the sole keeper of originals merely because it can answer questions about documents.

## Wiki, notes and preservation components

**SilverBullet's MIT server is the most direct optional Markdown/wiki component in this comparison.** The pinned server architecture separates file storage from client indexing and queries. That offers a usable context-editing surface without making a Markdown page the only possible digital source. Its PWA's offline storage is browser IndexedDB; attachments are not automatically all downloaded. Those capabilities differ from an ordinary fully hydrated workstation folder. The separate Desktop product has proprietary terms and cannot be included in the fully open-source path. [Pinned architecture](https://github.com/silverbulletmd/silverbullet/blob/2.12.1/docs/Architecture/Server.md), [browser synchronization](https://docs.silverbullet.md/Sync), [Desktop terms](https://silverbullet.md/terms)

SilverBullet could produce context that is registered back into MyBrain with its own identity and versions. Git-backed revisions can help, but do not supply historical label definitions, assignment validity or query evidence by themselves. The pinned HTTP API provides a practical file/revision integration seam. A third-party AI plug would require its own license and provider review. [Pinned HTTP API](https://github.com/silverbulletmd/silverbullet/blob/2.12.1/docs/HTTP%20API.md), [revision documentation](https://docs.silverbullet.md/Revisions)

**Joplin is stronger as a notes component than as the general file foundation.** Its open-source clients can synchronize through Nextcloud/WebDAV; the documented setup specifically warns against also synchronizing the Joplin sync folder through the Nextcloud desktop client. The separate Joplin Server has personal-use restrictions, so that server is outside this strict open-source path even though the clients remain eligible. [Nextcloud synchronization](https://joplinapp.org/help/apps/sync/nextcloud/), [server license](https://github.com/laurent22/joplin/blob/dev/packages/server/LICENSE.md)

Joplin now has meaningful desktop AI features, including local semantic search, so it would be inaccurate to dismiss it as a traditional notebook only. Its semantic index is local to the desktop and is rebuilt when the model changes. Note history uses periodic revisions and a default retention period, with the lowest configured retention across devices affecting preservation. These are not the required general source-history guarantees. [Semantic search](https://joplinapp.org/help/apps/ai_semantic_search/), [note history](https://joplinapp.org/help/apps/note_history/)

**Trilium is a plausible structured wiki alternative.** Its single-user, SQLite-centered design, attributes and scripting support a rich personal knowledge workspace; they are a different storage experience from arbitrary ordinary files. Live LLM documentation describes local-model integration but also limitations around note-level tool permissions and attribute history. Some live documentation refers to versions beyond the inspected v0.106.1 release, so those AI features cannot all be credited as shipped in that tag. [Project setup and storage model](https://triliumnotes.org/docs.triliumnotes.org/user-guide/setup/get-started/get-started/), [version-sensitive LLM documentation](https://docs.triliumnotes.org/user-guide/llm)

**Syncthing and Perkeep solve narrower problems.** Syncthing can transport ordinary files, but versioning is off by default and versions primarily concern changes received from other devices, not every local state. Its events API is useful observation infrastructure rather than a complete source audit. [Versioning semantics](https://docs.syncthing.net/users/versioning.html), [events API](https://docs.syncthing.net/dev/events.html) Perkeep's blob and permanode/claim model is an architectural reference for durable identity and changing descriptions. Its own site presents it as unfinished and technical; that is insufficient evidence for a complete everyday digital-brain interface. [Project status](https://perkeep.org/), [schema model](https://perkeep.org/doc/schema/)

Solid is also relevant as a separation-of-responsibilities reference: applications and user-controlled storage need not be the same product. Community Solid Server is an open-source modular server foundation, but this review did not establish the complete native-file, historical-memory and AI workflow on top of it. It is a useful architectural reference, not the leading integrated candidate here. [Solid's model](https://solidproject.org/about), [Community Solid Server](https://github.com/CommunitySolidServer/CommunitySolidServer)

## License gates and projects not advanced

Seafile Community remains a legitimate open-source file-service candidate; it should not be confused with the proprietary Professional edition. The reason not to advance its modern integrated AI path is more specific: the official maintainer stated that the metadata server was distributed as a Docker image without source, and Seafile AI requires that component. An open-source AI repository does not make the whole required chain open source. The block-based storage model also differs from a directly readable ordinary server tree. [Maintainer statement](https://forum.seafile.com/t/license-for-seafile-ai-metadata-server-thumbnail-server-and-seadoc/25295), [AI dependency documentation](https://manual.seafile.com/13.0/extension/seafile-ai/), [Professional license](https://manual.seafile.com/13.0/introduction/seafile_professional_edition_software_license_agreement/), [storage data model](https://manual.seafile.com/13.0/develop/data_model/)

Other exclusions are similarly scoped. Onyx has an open-source Community path, but the documented automatic connector permission synchronization is an Enterprise feature; that required capability cannot simply be credited to Community. Open WebUI's current license adds branding restrictions and exceptions, so its available source does not meet the unrestricted open-source gate used here. Anytype's client license restricts allowed networks and commercial scenarios. [Onyx license boundary](https://github.com/onyx-dot-app/onyx/blob/main/LICENSE), [connector permissions](https://docs.onyx.app/overview/core_features/connectors), [Open WebUI terms](https://github.com/open-webui/open-webui/blob/main/LICENSE), [Anytype client terms](https://github.com/anyproto/anytype-ts/blob/develop/LICENSE.md)

AFFiNE has mixed Community and Enterprise licensing rather than being uniformly closed. It would require a component-specific capability review before qualifying a complete path. Logseq's database/mobile transition and SiYuan's application-specific note storage make them weaker matches for the ordinary-file and durable general-source requirements in this shortlist; paid features alone are not the basis for that judgment. [AFFiNE backend license](https://github.com/toeverything/AFFiNE/blob/canary/packages/backend/server/LICENSE), [Logseq project status](https://github.com/logseq/logseq), [SiYuan storage and synchronization guidance](https://github.com/siyuan-note/siyuan/blob/master/README.md)

This is a screening outcome, not legal advice or a finding that restricted products are unusable for other purposes. A future selection must recheck exact component versions, dependencies, models and deployment terms. Commercial support for a fully open-source component remains compatible with the research goal.

## What to reuse and what remains to be designed

The strongest reuse boundary is the routine file/workspace service: clients, hydration and synchronization, authentication integration, previews, downloads and supported editing routes. A wiki component can supply an editable context interface. An AI component can supply extraction, embedding, retrieval and generation. Those are substantial savings, even though none is the entire brain.

The authoritative memory still needs explicit treatment of source identities and registered versions; description definitions and their origins; label assignments and applicability history; stored context as a new reusable source; contract versions; and the actual basis and result of historical queries. This is the meaning of “additional work,” not a decision to build a new universal database or duplicate every platform feature.

An API-first prototype should establish these boundaries before proposing a core fork. File events or watchers may trigger recognition, but a registration acknowledgment must distinguish observation from preserved capture. A processing outcome must identify the registered version it processed. Search indexes can then be rebuilt or replaced without silently rewriting source history. These are candidate integration responsibilities derived from the accepted principles, not capabilities established merely by installing an app.

Authorization is an equally important boundary. An asynchronous index ACL is not sufficient evidence for direct prospective revocation. A proposed design must show how the authoritative decision applies at the release boundary, including cached retrieval, running generation and stored derived context within the declared scope. Whether a given component can participate without invasive changes remains to be tested.

The comparison therefore supports a conditional order: **first Nextcloud as the integrated platform candidate; second OpenCloud as the storage challenger; then an optional AnythingLLM and wiki comparison only where the first journeys expose a need.** Khoj remains a useful alternate assistant. Perkeep and Solid inform architecture rather than replacing the end-user platform selection. No combination is declared compliant just because its boxes can be connected.

## Synthetic validation before a platform decision

A bounded comparison should use newly created synthetic documents, users and context. These journeys evaluate the unresolved contracts rather than recreating real private ingestion. The first run should compare Nextcloud and OpenCloud on the same file lifecycle; AI and wiki components are added only where needed.

| Journey | Synthetic operation | Evidence needed for a useful result |
| --- | --- | --- |
| Ordinary offline work | Hydrate a PDF and editable document, disconnect, edit in a native application, reconnect. | Actual available local files; distinguish local change, recognition, registered version and processing completion. A placeholder or queued upload is not counted as capture. |
| New device and mobile | Preview compatible content; download an unsupported original; edit and return a new version through a supported route. | Original bytes remain retrievable, identity/version changes are explicit, and preview limitations do not exclude registration. |
| Required version preservation | Register A, B and C, including rapid saves and same-timestamp edge cases; change retention settings and restore. | Every agreed registered version survives and is distinguishable. Intermediate keystrokes are outside the claim unless explicitly included. |
| Local deletion | Delete a synchronized working copy and reconnect. | The deletion is recognized without silently destroying required registered history. Any destructive action follows the owner's explicit decision and declared scope. |
| Rename, copy and conflict | Rename through the service, change external storage directly, copy, and create a two-device conflict. | Identify which operation preserves identity, creates another item or leaves an unresolved observation. Locally retained conflict content must not masquerade as centrally registered. |
| Stored context and labels | Produce wiki context from A; save a new label with its originating context version; reuse the label elsewhere; later withdraw an assignment. | Origin remains distinct from assignment. Both context and sources are selectable; historical applicability survives without requiring duplicate rationale on every use. |
| Historical query | Record a query and its result, then change a source, label applicability and retrieval method. | Recover what actually supported the earlier result, alongside a separately identified current answer. Current citations alone are insufficient. |
| Revocation during generation | Pause a synthetic answer after retrieval, revoke a right, and resume; repeat with queued indexing and cached results. | No further unreleased information under the revoked right after the declared effective point. No promise to recall information already delivered. |
| Model/index replacement | Rebuild embeddings or change the model, then restore from backup. | Original versions, descriptive history and earlier query evidence remain available; a rebuilt current index is not mistaken for recovered historical evidence. |
| Coverage and unsupported inputs | Include a binary, encrypted file, oversized document and deliberately failed processor. | Registration remains possible where authorized; processing gaps and unknown completeness stay visible. Empty search does not prove nonexistence or disclose inaccessible items. |

The outcome should separate supported behavior, configuration-dependent behavior, missing behavior and unresolved evidence. Partial results can be useful, but usability must be judged by the applicable contract or authorized recipient. A successful upload, empty queue or plausible answer is not a substitute for the declared scope of completeness.

A candidate should advance only with an explicit explanation of its remaining gaps and a credible extension boundary. Failure of an AI app need not disqualify the file service; failure to preserve required registered versions or enforce the declared release boundary cannot be hidden by a polished interface. These journeys produce decision evidence, not a new implementation approval.

## Remaining uncertainty and decision boundary

This report establishes a focused shortlist, not a tested architecture. The main unknowns are end-to-end version registration, portable restoration of identities and histories, exact source-version citations, mobile edit return paths, processing coverage, and authorization changes during active disclosure. Documentation/code discrepancies and rolling documentation need release-specific validation.

The memory layer may reuse existing versioned stores or preservation components; “additional work” means MyBrain-specific integration, models and guarantees, not inventing every mechanism from scratch. TerminusDB's open-source versioned structured-data approach is another component-level reference, not a demonstrated complete offline workspace. [Project and architecture](https://github.com/terminusdb/terminusdb), [license](https://github.com/terminusdb/terminusdb/blob/main/LICENSE)

The recommended next step is a separately authorized synthetic comparison of the leading file platforms, followed by a decision on their role. Runtime, database, model, wiki format, deployment host and final interface choices remain open. The original email-ingestion and NAS implementation are not resumed by this research.
