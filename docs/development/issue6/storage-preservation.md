# Payload preservation, destruction and recovery

**Status:** Design candidate — review requested  
**Version:** 1.1  
**Last Updated:** 2026-10-28

## Purpose

Specify the durable-byte boundary and failure-safe custody operations across PostgreSQL and retained files, including exact limits of destructive claims.

## Summary

Prepare immutable bytes before publishing references. OpenCloud is a mutable working environment. Coordinated backup holds and a non-rewound restore guard prevent an old backup from silently resurrecting owner-destroyed data. Unsupported erasure guarantees are rejected rather than reported as completed.

## Retained-byte preparation

The archive is an owner-controlled POSIX filesystem namespace owned by the registrar service and excluded from OpenCloud mounts, shares and desktop synchronization. Only the payload writer creates objects; only the explicitly authorized destruction worker removes admitted objects. Payloads are not globally deduplicated: identical bytes belonging to independent items receive different payload IDs/objects, avoiding cross-item deletion coupling. Within an item, explicit payload reuse across revisions is allowed and inventoried.

Server-generated relative keys are objects/{payload_uuid}.bin and pending/{operation_uuid}/{payload_uuid}.{fence_uuid}.part. Caller paths, symlinks, hardlink imports and cross-mount promotion are rejected. The root and generated parent directories are trusted service-owned directories. Create temporary files exclusively (O_CREAT|O_EXCL and no symlink following); stream with bounded buffers, count bytes and hash SHA-256 over exact received bytes. Reject truncation/excess length or expected-hash mismatch and retain failure evidence; do not publish a retained payload.

Complete preparation fsyncs the file, promotes on the SAME filesystem with renameat2(RENAME_NOREPLACE), then fsyncs destination directory and every newly created ancestor directory. Ordinary replacing rename and a copy/delete fallback are forbidden. While finalizing, hold the operation row lock, verify the current attempt fencing token, perform promotion and record prepared_payload ready in that transaction. Do not hold the registry publication lock during streaming or filesystem I/O. A stale attempt may leave its private partial file but cannot publish/promote over another attempt. Existing destination after a crash is reconciled by exact length/hash against the immutable operation intent before adopting it.

fsync/rename capability, actual filesystem, mount durability and device behavior must be admitted through native fault-injection evidence in implementation. Unsupported fsync, EXDEV, EIO or ENOSPC returns DURABILITY_UNAVAILABLE/INSUFFICIENT_STORAGE, never a weaker silent acknowledgment. These platform requirements are fixed; deploying on an incompatible host is unsupported, not an unresolved design alternative. Host/root administrators remain trusted; permissions are not WORM.

Exact compact bytes use PostgreSQL bytea, not jsonb-only storage. Source JSON text is retained byte-for-byte; any parsed JSONB representation is a separately identified derivative. The model's 1 MiB limit chooses backend, not source meaning. Once all inline/file payloads are ready, one registry publication makes all source/component/binding references visible. A mixed source can also deliberately point to known incomplete candidate parts; that is a complete registration of an explicitly partial capture, not a claim all original content was received.

## Crash and reconciliation behavior

| Crash or failure boundary | Required durable observation and recovery |
| --- | --- |
| Before prepare commits | No successful operation exists; repeat same operation ID or query. No source identity was promised. |
| During byte reception | Only private operational partials; an already registered candidate source keeps its existing identity/history. Resume is explicit and revalidates fences. |
| After file fsync but before no-replace promotion | Pending object remains; no source publication references it. Verify length/hash before resuming. |
| After promotion but before ready-row commit | A retained file may exist without a ready descriptor. Reconcile exact operation/payload IDs; never overwrite or automatically purge it. |
| After ready descriptor but before publication | Preserved bytes exist but new combined state is unpublished. Current/historical registry views retain their prior complete basis. |
| During publication or CAS conflict | All registry changes roll back; ready payloads remain recoverable, not falsely admitted or deleted as orphans. |
| Publication committed but response lost | Same operation ID returns exact committed result after durable query. No duplicate source or new receipt from a transport retry. |
| Read detects corruption/missing bytes | Return explicit current custody failure and record separate attributable evidence; never replace historical content with newer bytes. |

Reconciliation is a privileged bounded operation, not an implicit write side effect of GET. It compares prepared payloads and existing retained objects with operation/publication records, then reports or finishes only a matching authorized pending intent. Foreign objects remain unknown pending evidence. No TTL garbage collection deletes admitted bytes or unresolved capture artifacts. A separate owner-authorized cleanup plan can target unadmitted partials explicitly.

Content reads record expected stored length/hash. For a full streamed read, compute hash/count while reading; hold the final output unit until EOF/hash/length match. On mismatch do not release the final unit or complete the response; the client also verifies recorded length/hash before treating the download as complete. Earlier released units cannot be recalled. Zero-byte payloads validate before response completion. This is an integrity contract for complete reads, not a proof every previously released partial byte was correct. Range reads are not supported by v1. Regular integrity audits use the same immutable payload IDs; a mismatch becomes visible evidence, not a new source version.

## Custody controls and lock order

These operational control tables are normative here; source/component tables remain normative in storage-model.md.

| Table | Required columns and rules |
| --- | --- |
| release_control | singleton smallint=1 PK, generation bigint>0 | One durable global counter, initialized once with a new registry and never reused/decremented within a service incarnation. Updated in the SAME transaction as each barrier install/change/removal under EXCLUSIVE maintenance. Counter overflow fails closed as DURABILITY_UNAVAILABLE. |
| custody_barrier | item_id uuid PK/FK item, destruction_id uuid, installed_at timestamptz | Blocks new publication/reference/release for the scoped item; never interpreted as a label. Deleted only through approved cancellation or final scoped removal, with a fresh release generation in the same transaction; deleting the row never clears the generation fence. |
| custody_job | job_id uuid PK, kind destruction/backup/restore/reconcile, intent jsonb, state text, evidence jsonb, incarnation uuid, created_at/updated_at timestamptz | Per-kind state contracts below; intent/evidence are managed sensitive copies included in inventory. |
| backup_inventory | backup_id uuid PK, basis uuid FK publication, manifest_payload uuid, guard_sequence bigint, state preparing/complete/incomplete/destroyed, locations jsonb | Complete requires verified database dump, every selected retained object, configuration/version manifest and restore-guard linkage. |
| restore_guard | A separate durable signed journal, not a table restored from an old DB image | Sequence, previous-record hash, owner-approved destructive scope IDs, action intent/cancel/completed and evidence fingerprint. HMAC-SHA256 with an owner-held secret; contains no source plaintext. It is sensitive retained control data whose lifecycle is part of destruction scope. |

Lock order: maintenance/custody advisory lock first, then registry_clock if needed, then operation/item rows in UUID order. Session release locks are last. Ordinary publisher, file finalizer, backup and release units take SHARED maintenance holds. A destruction barrier installation, destructive filesystem step or guard update takes EXCLUSIVE maintenance hold; it waits for in-flight release units to leave. Revocation only locks its session row and does not acquire maintenance/registry locks, avoiding inverse lock order.

Every protected release unit obtains the shared maintenance hold, then the session lock and fresh READ COMMITTED custody/session checks on a control connection. The request captured its original incarnation/generation under that shared hold BEFORE its first protected snapshot/cache lookup/open/prefetch. Each unit also compares that context to CURRENT release_control. Barrier installation/change/removal increments the durable generation while holding EXCLUSIVE maintenance; publication and the increment commit together. In-flight requests with older snapshots, open descriptors, cached plaintext or queued units remain invalid even after final deletion and barrier removal, because generation never returns to their value. A mismatching request must discard/close that state and cannot renew its context; only a fresh request using a new current existence lookup may proceed. Old cache entries cannot be reused or retagged. Nothing relies on unlink closing another reader's descriptor or waiting only for currently active release units. A historical REPEATABLE READ snapshot is never used as the current authorization/barrier check. The destructor installs barriers and commits while holding EXCLUSIVE maintenance; its effective boundary is that commit. No later protected release can pass a barrier, including metadata/known existence about scoped destroyed items. Already released units cannot be recalled. No I/O wait outside a bounded release unit is allowed to hold the release lock. Native OpenCloud is not mounted on the archive and cannot bypass these controls.

HMAC integrity does NOT prove that a guard is the latest copy: an entire older valid journal can be replayed. Admission therefore requires a trusted owner-controlled freshness anchor (latest destructive-intent sequence and journal-head hash) outside the PostgreSQL/archive rollback domain and outside those ordinary backup sets. The owner keeps that recovery receipt independently, for example on a separately administered device; no special hardware is required. Independence and freshness are explicit operational trust assumptions, not facts established by a signature. A deployment unable to establish that authority cannot claim safe restore and remains offline on recovery.

POST /v1/destruction-plans/{plan}/execute first returns202 with {job_id:UUID,state:pending,guard_anchor:{sequence:decimalString,head_hash:Hash}} after durable intent/barrier installation. Before irreversible removal, POST /v1/custody-jobs/{job}/anchor-confirmation requires authenticated owner confirmation of {schema_version,incarnation,operation_id,sequence,head_hash,independent_copy_confirmed:true}. This attests that the owner preserved the receipt outside the rollback domain; the server does not claim to prove physical independence from that boolean. Missing confirmation leaves pending without deletion. Any later cancellation/checkpoint that permits disclosure after removing suppression needs the same independently retained anchor before that effect. Restore requires the latest owner-held anchor; a guard older than it or lacking its exact prefix/hash fails closed. A stale anchor supplied by the trusted owner violates the stated recovery assumption and is not cryptographically detectable.

The restore guard survives DB rollback independently: append and fsync destructive intent BEFORE committing barriers or deleting content. A crash after guard intent but before DB state is conservative: reconcile/restore installs the pending barrier instead of exposing data. Signed cancellation is allowed before irreversible effects; after any destructive effect it cannot pretend lost data was restored. If the current guard/key is missing, corrupt or older than a backup requires, restoration remains offline. Never silently initialize an empty replacement guard for an existing repository.

## Explicit destruction contract

POST /v1/destruction-plans accepts {schema_version,incarnation,operation_id,item_ids:UUID[],include_versions:true,include_derivatives:boolean,include_backups:boolean,residual_mode:identity_tombstones/none,required_guarantee:managed_objects/physical_media}. It is owner-authorized preview only. v1 supports whole-item destruction: include_versions MUST be true, selecting ALL persisted revisions of each listed item, including unselected branches, its head-selection history and owned payloads; the resulting exact scope inventories the corresponding body/edge/operational copies. include_versions:false returns422 UNSUPPORTED_DESTRUCTION_SCOPE before plan creation, guard/barrier changes or destructive effects. Unknown revision-only selector properties remain422 INVALID_ENVELOPE under the closed envelope, with the same no-effect boundary. No current-head default, implicit revision choice or silent widening is permitted. Related items/components are handled by the explicit preview/dependency rules below; whole-item scope does not silently authorize their deletion. Response is {plan_id,plan_hash,basis,exact_scope,dependent_refs,managed_locations,external_or_unknown_locations,guarantee_supported,irreversible_effects}. The scope includes payload bytes, description canonical bodies, parsed derivatives, bindings/manifests, operation intents/results, caches, control copies and known backups/WAL/snapshots where requested. Reference registration never gives permission to delete an external target.

The preview computes affected closure without deleting. If a payload/component is still required by outside-scope history, return409 SHARED_DEPENDENCY and list authorized affected IDs; do not widen scope or silently damage retained history. The owner may revise scope. No default classification/lifecycle rule authorizes actual deletion. POST /v1/destruction-plans/{plan}/execute requires {schema_version,incarnation,operation_id,plan_hash,owner_approval:true}; changed basis/dependencies require a fresh plan/hash. Explicit authenticated approval refers to THIS exact preview, not a generic label or automatic TTL. IDs do not become a right to erase an external source.

Managed_objects means removing the explicitly inventoried managed objects/records from normal retrieval and managed restore, not a claim of forensic media erasure. Physical_media requires verified erasure of all relevant physical remnants, WAL and copies. The baseline POSIX/PostgreSQL adapters DO NOT support that stronger guarantee: reject UNSUPPORTED_ERASURE_GUARANTEE before destructive effects, not a perpetual hidden TODO. An owner requesting all copies cannot receive a completed claim while any relevant backup, snapshot, WAL or external location is unverified/unreachable. SQL DELETE, VACUUM or unlink alone is never reported as proof of physical erasure.

Execution states: preview,blocked,pending,active_removed,pending_copies,completed,failed. Install guard intent and custody barriers before any effect; suppress reads immediately at the declared barrier boundary. Remove only planned objects through privileged deletion; all body/edge projections and managed copies in the exact logical scope are removed together or remain explicitly partial. FK-referenced identities may retain explicit tombstones ONLY if residual_mode permits them. With none, closure must include referring records or the plan is blocked; do not silently leave hashes, origin identifiers or copied descriptions. completed is scoped to the supported declared guarantee and requires verified disposition for every in-scope managed location. Out-of-reach copies leave pending_copies and a clear list; they are not 'destroyed'. A failure after some removals cannot restore already destroyed bytes and must not claim rollback.

The guard keeps suppression knowledge until every managed restore path containing that scope has been removed or reconciled. With residual_mode=none, purge scope-bearing guard/operation records only after those restore paths are proved absent and atomically advance the guard checkpoint; if that cannot be established, the job remains incomplete. A receipt/tombstone cannot reconstruct deleted history. Physical remnants outside the expressly supported managed-object guarantee are stated before approval, never hidden behind a completed physical-erasure label.

## Joint backup and restore

POST /v1/backups accepts {schema_version,incarnation,operation_id} and returns202 {job_id:UUID,state:preparing}; the destination is a server-configured private backup namespace, never a caller path. It is an owner-controlled idempotent operation creating a backup job. Hold shared maintenance protection against destructive work for the entire capture. Begin a REPEATABLE READ transaction, export its snapshot and select basis/publication plus ALL retained payload descriptors in that exact database snapshot. Run pg_dump --snapshot with the SAME live exported snapshot while the exporting transaction remains open. Include inactive branches/history and referenced control records; copying only current heads is insufficient. Copy every selected immutable file into a private backup namespace and verify each length/hash. Ongoing additive publication is allowed; later content is not in this backup. Do not delete referenced objects while the hold is active.

The backup manifest contains backup UUID, exact basis UUID, database dump hash, every retained payload ID/key/length/hash, registry/schema/core-validator versions, PostgreSQL major and full installed version, OpenCloud/reva adapter baseline if used, guard sequence/hash, capture status and required owner-secret/config references without secret values. Roles/extensions/privilege configuration need explicit protected configuration backup; a single-database pg_dump does not include all global objects. The complete marker is written/fsynced last, only after all parts are verified. A DB dump alone or an interrupted file copy is incomplete. Backup credentials/keys are protected independently and never embedded in public artifacts.

Restore is offline, fail-closed and owner-authorized; no writer/release service is exposed during reconstruction. Validate complete manifest and all hashes, restore into a separate empty database/archive, restore required trusted config/secrets and preserve all surviving item/revision/payload/publication UUIDs. Load the CURRENT independently retained restore guard, reapply pending/completed destruction suppressions and reconcile every outbox effect before opening writes. Old external operations may already have happened; never blindly replay them. If guard freshness or known destructive scope cannot be established, return RECONCILIATION_REQUIRED and stay offline.

GET /v1/custody-jobs/{job} returns {job_id,kind,state,evidence,remaining_locations,guard_anchor} under owner control. Backup/restore job IDs and mutations require incarnation and idempotent operation identity, and their request/result copies join the managed inventory. Offline Restore uses {schema_version,incarnation,operation_id,backup_id,manifest_hash,current_guard_anchor,owner_approval:true}; source-specific external targets are never contacted by restoration itself.

Generate a NEW service incarnation, initialize a fresh release context and invalidate old owner sessions, cursors and operation retry contexts before reopening. All old service processes/read contexts, descriptors, snapshots, caches and transport queues must be stopped/discarded before exposure; a restored release_control value cannot revive them because incarnation changed. On an ordinary restart without restore, generation is loaded durably and is never reset. Public historical basis UUIDs survive where restored; an old post-backup publication UUID that is absent returns HISTORICAL_BASIS_NOT_RESTORED rather than using an internal ordinal now assigned to another commit. OperationId+old incarnation cannot trigger a fresh write. Current views use only restored/reconciled data and report the recovery cutoff; they do not invent lost post-backup events. No live migration or replacement is authorized by this design.

## Platform and primary evidence

Selected production primitives: PostgreSQL 18 core with fsync=on, synchronous_commit=on and supported durable local storage; Linux filesystem supporting exclusive creation, no-replace same-filesystem promotion and directory fsync. Exact patch/image/driver/runtime pins are mandatory implementation/deployment admission records, not an unsupported assertion that the present host has passed. Core registration requires no pgvector, event store, distributed transaction coordinator, Wikibase or SQLite. The selected retained adapter is Linux-specific; an unsupported host must use another proved adapter under the same contract, not silently lower durability.

OpenCloud compatibility evidence remains pinned to 7.2.4 with reva 2.46.8. Supported native working-file routes include WebDAV GET/HEAD/PROPFIND and known-length PUT; no If-None-Match create-only, atomic native capture or all-edit retention guarantee is inferred. OIDC owner authentication is an external working-file integration concern; a WebDAV app token is not assumed to be a scoped connector credential. No native OpenCloud endpoint serves the protected retained namespace.

Primary sources: [OpenCloud dependency pin](https://github.com/opencloud-eu/opencloud/blob/v7.2.4/go.mod), [inspected PUT](https://raw.githubusercontent.com/opencloud-eu/reva/v2.46.8/internal/http/services/owncloud/ocdav/put.go), [WebDAV](https://docs.opencloud.eu/docs/dev/server/apis/http/webdav/), [fsync and directories](https://man7.org/linux/man-pages/man2/fsync.2.html), [no-replace rename](https://man7.org/linux/man-pages/man2/rename.2.html), [exclusive open](https://man7.org/linux/man-pages/man2/open.2.html), [unlink limitations](https://man7.org/linux/man-pages/man2/unlink.2.html), [PostgreSQL durable commits](https://www.postgresql.org/docs/18/runtime-config-wal.html), [MVCC/vacuum limits](https://www.postgresql.org/docs/18/routine-vacuuming.html), [WAL recovery](https://www.postgresql.org/docs/18/wal-intro.html), [pg_dump snapshot](https://www.postgresql.org/docs/18/app-pgdump.html).
