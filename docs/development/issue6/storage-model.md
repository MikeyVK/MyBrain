# Storage registration model and constraints

**Status:** Design candidate — review requested  
**Version:** 1.1  
**Last Updated:** 2026-10-28

## Purpose

Specify the logical records, typed payloads and PostgreSQL constraints needed to implement MyBrain registration without copying whole source descriptions for each change.

## Summary

One owner, one registry database, immutable revisions and transactional head-selection history. A source's combined historical state is (source item, published commit); unchanged components are shared by exact reference. An explicit result manifest freezes the revisions actually used. No custom persistent-tree or event-replay engine is required.

## Scalar and null conventions

All IDs are application-generated UUIDv4 strings, lowercase canonical spelling; the database type is uuid. IDs identify records, never imply equality of content or identity outside MyBrain. CommitId/BasisId is an immutable UUID identifying a publication. PublicationOrdinal is a positive signed bigint used only internally for serialized ordering, never an external basis identity. Operation/retry/cursor contexts carry an additional service-incarnation UUID; restoring a database creates a new incarnation before reopening. UtcTime is an RFC3339 UTC string with microsecond precision, stored as timestamptz. Hash is lowercase SHA-256 hex over an explicitly defined byte input. Unknown optional information is JSON null; absent required members, duplicate JSON keys, NaN/Infinity, unsafe integers and unrecognized core-envelope properties are rejected. Optional extension content lives only in the declared attributes object. Empty bytes, empty lists and empty text are valid and distinct from null.

The component body is encoded as canonical UTF-8 using RFC8785 JCS profile mybrain-jcs/1. Decimal values needing more than IEEE754 precision use decimal strings under their contract; dates and large identifiers are strings. Canonicalization is for descriptions/requests only. It never replaces exact received source bytes, which are retained as a Payload. The same bytes in two items never merge their identities. Canonical-body equality may permit explicit reuse, not silent coalescing. See [RFC8785](https://www.rfc-editor.org/rfc/rfc8785.html).

## Registry tables

This is a relational contract, not an executable migration. All ordinary writes use the publisher; physical migrations and privileged destruction are separate capabilities. NOT NULL is the default below; '?' is the only nullable marker. No ON DELETE CASCADE is permitted for ordinary records.

| Table | Columns | Keys and constraints |
| --- | --- | --- |
| registry_clock | singleton smallint=1, last_ordinal bigint>=0, current_publication uuid?, incarnation uuid | PK(singleton); one row locked before publishing; FK(current_publication,last_ordinal) to publication(commit_id,ordinal) when non-null; null only at empty ordinal0; sequence allocation is not a commit clock. |
| publication | commit_id uuid, ordinal bigint>0, operation_id uuid, recorded_at timestamptz | PK(commit_id), UNIQUE(ordinal), UNIQUE(commit_id,ordinal), UNIQUE(operation_id); FK operation; timestamp is observation, not ordering authority. |
| item | item_id uuid, role text, created_commit uuid, head_revision uuid?, head_publication uuid? | PK(item_id); role in source/metadata/definition/assignment/relationship/representation/contract/receipt/package/binding/manifest; role immutable; head non-null at commit for an ordinary item. |
| revision | revision_id uuid, item_id uuid, parent_revision uuid?, contract_revision uuid?, canonical_body bytea, body jsonb, body_hash bytea, commit_id uuid | PK(revision_id), UNIQUE(item_id,revision_id), UNIQUE(item_id,commit_id); hash octet_length=32; jsonb object; FK item/publication; FK contract_revision to revision; parent composite FK to same item's revision, DEFERRABLE INITIALLY DEFERRED. |
| head_selection | item_id uuid, commit_id uuid, ordinal bigint, revision_id uuid | PK(item_id,commit_id), UNIQUE(item_id,ordinal), UNIQUE(item_id,commit_id,revision_id); FK(commit_id,ordinal) to publication; FK(item_id,revision_id) to revision; append-only. Every new item or head change inserts exactly one row and updates item.head_revision and item.head_publication in the same transaction. |
| revision_edge | from_revision uuid, field text, ordinal int>=0, target_item uuid, target_revision uuid? | PK(from_revision,field,ordinal); FK from revision; target item FK; exact targets use composite FK(target_item,target_revision); null target_revision means identity-only. |
| binding_index | revision_id uuid, subject_item uuid, subject_revision uuid?, slot text, member_item uuid, member_revision uuid, attached boolean | PK/FK revision; subject FK; optional exact subject revision belongs to subject; member composite FK; reflects the canonical binding body exactly. |
| prepared_payload | operation_id uuid, payload_id uuid, owner_item uuid, byte_length bigint, sha256 bytea?, backend text, inline_bytes bytea?, retained_key text?, state text | PK(operation_id,payload_id), UNIQUE(payload_id); FK operation; future owner_item may not yet exist; state declared/receiving/ready/in_doubt. Private operational staging, never source authority. Publication validates owner and moves prepared descriptor/data into payload atomically. |
| payload | payload_id uuid, owner_item uuid, backend text, byte_length bigint>=0, sha256 bytea, inline_bytes bytea?, retained_key text?, prepared_operation uuid | PK(payload_id), UNIQUE(owner_item,payload_id); FK owner_item to item; FK prepared_operation to operation; backend inline/retained-file; exactly one body location matches backend; bytea hash length32; inline length equals byte_length; retained_key server-generated and unique. |
| operation | operation_id uuid, request_hash bytea, request_body jsonb, state text, result jsonb?, publication_commit uuid?, created_at/updated_at timestamptz | PK(operation_id); state prepared/receiving/ready/committed/failed/in_doubt; committed iff publication_commit and result are set. State is recovery machinery, not source lifecycle taxonomy. |
| operation_attempt | operation_id uuid, attempt_no bigint, fencing_token uuid, outcome jsonb?, observed_at timestamptz | PK(operation_id,attempt_no); current attempt fenced by operation row lock. Immutable completed-attempt evidence; no unbounded blind retries. |
| outbox | task_id uuid, operation_id uuid, kind text, target jsonb, completed_at timestamptz? | PK(task_id); unique logical task key; publication-time insertion; adapters never infer authority from arbitrary source text. |

FKs cannot establish cross-row semantic constraints alone. The publisher validates canonical bytes/hash against body, same-item parent/head lineage, role/profile compatibility, edge extraction, binding projection, exact referenced closure and payload preparedness while holding the publication lock. It rejects missing, future or destruction-blocked references. Parent, content-part containment and declared derivation dependencies must be acyclic; ordinary semantic relationships may be cyclic even when endpoints pin revisions. Validation traverses only affected containment/derivation paths, with max 100,000 visited nodes/edges per command; larger requested validation/expansion returns LIMIT_EXCEEDED before publication, not rejection merely because unrelated old history is large. Historical revisions do not become current solely by creation; explicit head changes are mandatory. item.head_publication is the commit_id of its most recent head_selection, including a selection that returns to an older revision. CAS compares both expected_revision and expected_selection_publication (null/null only for an absent item), preventing ABA stale writes. Linear selected revisions parent the expected selected head. Branch revisions may parent an older revision of the same item without changing the current selection; selecting that branch is a separate explicit CAS action. An explicit select-existing operation may choose an older revision without pretending its intermediate history disappeared.

head_revision and head_publication must be either both null or both non-null; a DEFERRABLE composite FK(item_id,head_publication,head_revision) references head_selection. Null heads are permitted only inside a new-item transaction before its final selection. Exact edge targets use a mandatory target_item and nullable target_revision: null explicitly means identity, otherwise the composite FK enforces ownership (MATCH SIMPLE deliberately permits the identity case). Binding exact subject ownership is checked similarly. binding.slot restricts member role: metadata→metadata, label→assignment, representation→representation, relationship→relationship, basis→manifest/source. Binding subject may be ANY registered item role, including a definition or contract; an exact subject revision must belong to that item. Generic item views resolve bindings with the same rules, so descriptions of descriptions do not require a duplicate raw-source authority. One binding item has one selected revision per publication, but multiple binding items for the same subject/slot are allowed, preserving different assessments. Body/projection checks and role checks execute inside the controlled publisher; CHECK clauses do not pretend to enforce cross-row rules.

The ordinary database role cannot UPDATE/DELETE immutable publication, revision, head_selection or completed attempt rows; it cannot execute DDL. Only the controlled publisher/maintenance interfaces receive the required narrowly scoped DB privileges. A transaction guard verifies exactly one publication marker for all immutable changes and consistent head projections. Privileged administrators remain trusted; this is not WORM or protection against host takeover.

## Typed revision bodies

Every row below defines a closed core object. Array order is preserved. Exactly referenced targets carry both item_id and revision_id; storage verifies ownership. The revision envelope supplies item/parent/contract/commit; bodies do not repeat those fields.

| Role | Required body members and cardinality | Optional/nullable members and interpretation |
| --- | --- | --- |
| source | content: ContentOrNull; parts: Part[0..10000] | attributes: object defaults {}; source type is not fixed by the envelope. Produced context is an ordinary source with declared derived origin. |
| metadata | attributes: object; basis: ExactRef[0..10000] | Observations versus supplied claims are explicitly distinguished by the governing metadata contract, never inferred from value shape. |
| definition | name: nonempty string; meaning_payload: PayloadRef; origin: Origin | Origin = known exact source/context reference(s), or unknown with an explicit reason. New definitions retain origin; reuse does not replace it. |
| assignment | definition: ExactRef; target: ItemOrExactRef; assessment: object; basis: ExactRef[0..10000] | confidence: {value: finite number, scale: ExactRef} or null. Scale is contract-described, not automatically probability. Assessment vocabulary/applicability is declared by contract; no universal truth flag. |
| relationship | predicate: ExactRef; from: ItemOrExactRef; to: ItemOrExactRef; attributes: object | It may link identity or pin versions; pinned targets are never silently advanced. |
| representation | input: ExactRef[1..10000]; method: ExactRef; payload: PayloadRef; attributes: object | For vectors attributes must declare model/version identity, dimension>0, scalar_encoding float32/float64, and coordinate-space contract. Payload length and finite values must match that contract; compatible comparison is a separate operation. |
| contract | name: nonempty string; document: PayloadRef; format: nonempty string | Registration stores the contract as data. No automatic code loading, network schema resolution or activation occurs. |
| receipt | observed_at: UtcTimeOrNull; connection: opaque nonempty string; claims: object; matches: ExactRef[0..10000] | package: ItemOrExactRefOrNull; recognition_contract: ExactRefOrNull; upstream_binding: {status: verified/unknown/conflicting, evidence: ExactRef[]} required. A later receipt is independent from a transport retry. |
| package | claims: object; contents: ItemOrExactRef[0..10000]; expected_scope: object | Scope/completeness evidence belongs to ordinary descriptions; a package need not correspond one-to-one with a source. |
| binding | subject: ItemOrExactRef; slot: metadata/label/representation/relationship/basis; member: ExactRef; attached: boolean | subject exact revision limits the attachment to that content state; identity-only subject spans states until explicitly revised/withdrawn. The binding's history is independent. |
| manifest | source: ItemOrExactRef; basis_commit: CommitId; members: ExactRef[0..10000]; purpose: nonempty string | records the actual selected members/result inputs, not an automatically expanded person's whole profile. |

ContentOrNull is null (no content admitted yet), {mode:retained,payload:PayloadRef}, or {mode:reference,locator:nonempty string}. A reference locator is opaque stored data, never automatically fetched; its availability/integrity assertions need evidence. Part = {position:nonnegative integer, role:nonempty string, target:ExactRef}; positions are unique within a source revision. A mixed email can retain raw message bytes and pin exact attachment-source revisions. Unknown or missing external parts can be represented by pinned candidate source revisions with null content, never by pretending their bytes exist. PayloadRef = {owner_item:UUID,payload_id:UUID}; no consumer-supplied storage path.

A record itself is digitally representable and can be a target of descriptions; a contract or definition can also be preserved as a raw source before semantic registration. The finite structural roles are service envelope types, not prescribed content categories or label meanings. Contract extensions use attributes or a new admitted structural profile, preserving existing schemas; malformed core objects are never silently accepted.

## Contracts, definitions and attachments

Every non-contract revision pins a governing contract revision. The contract revision FK is null only on a contract record, validated by the built-in contract-envelope/1 profile; this terminates bootstrap recursion. Bootstrap installs exact canonical core-contract documents as contract items and binds those revision IDs to known validators in trusted deployment configuration. All other contract text is inert until an explicit authorized admission maps it to a compatible trusted validator. Stored scripts cannot execute. Imported unknown formats remain raw source content or inert contract records; an unsupported typed write returns CONTRACT_NOT_ADMITTED, preserving universal raw registrability.

Definition is not application. An assignment pins the definition revision whose meaning was used. Advancing a definition head does not migrate assignments. Reassessment creates a new assignment revision and, only when explicitly requested, advances relevant binding(s) in the same publication. Withdrawal creates a new detached binding revision; it does not erase old assignments. User corrections are new attributed revisions; autonomous consumers must name their basis and expected heads.

Descriptions are reusable as exact metadata-set revisions. Sharing a set does not share future edits: a later set revision affects a source only through an explicit binding-head change. Lifecycle is ordinary contract-described metadata on the same source, including after admission. No separate candidate registry or intake database exists. Staging is a read-only selector over selected current metadata; its membership neither proves preservation nor authorizes processing/destruction. Reconciliation records evidence; it does not reinterpret a pending lifecycle label as completed work.

## Combined versions and current views

All successful publications are serialized by registry_clock. In a REPEATABLE READ, READ ONLY transaction, take visible basis B=registry_clock.current_publication and resolve its internal ordinal O, then resolve each item's head as the head_selection with maximum ordinal<=O. One transaction's partial state is never visible. A source's combined-view coordinate is (source_item_id,B); its source content is the selected source revision, plus selected current binding revisions for that source and exact selected source version. An identity-targeted binding applies across source content revisions until detached; exact-targeted bindings are limited to the matching source revision. Return pinned member revisions, never substitute member item heads. The same registered-view algorithm applies to non-source items, including metadata, definitions and contracts; source content/parts are interpreted only for source-role bodies. Historical lookup uses the same algorithm for an explicit retained publication UUID B, subject to current authorization and destruction barriers.

B may advance for unrelated changes, so (source,B) is a view coordinate, not proof of a new semantic composition. The operation contract returns a fingerprint of the actual selected combination, independent of unrelated publications. No new row is required for every unchanged source whenever B advances. A component change stores only its new revision, head_selection and expressly changed bindings. Current views choose the newest visible B and may apply explicit caller selectors under their stored contract; storage does not choose semantic truth or automatically pick the newest address. If a new action uses address B instead of historical address A, the consumer selects under its action contract and submits a new manifest/source with the actual used revisions.

Ordinary stable pagination uses a basis-pinned authenticated cursor without writing a manifest. For a durable actual execution/input record, explicitly create an immutable manifest whose exact members are selected under one visible B. A later query is not proof an earlier result existed. The common read returns its basis and actual member refs even if no result manifest is persisted. Historical combined views can later become partially unavailable after explicit destruction; the service reports that loss rather than silently reconstructing with new values.

## Indexes and storage sizes

Required B-tree indexes: revision(item_id,commit_id), head_selection(item_id,ordinal DESC), binding_index(subject_item,subject_revision), revision_edge(target_item,target_revision), publication(operation_id), payload(owner_item), operation(state,updated_at), outbox(completed_at). Add GIN jsonb_path_ops on metadata body attributes for explicitly supported equality/containment filters. Body/inline bytes are not duplicated into logs or operation outcomes. Source plaintext search/vector nearest-neighbor indexes are replaceable derived consumers, not an additional authority or mandatory dependency; exact ID/metadata/label retrieval is defined in the operation contract.

Inline content is limited to 1 MiB per payload; larger content always uses retained files. The threshold selects a backend, not a semantic source class. A generic retained-file stream supports up to the signed bigint byte-count range subject to configured free-space/quota admission; the wire API has explicit declared length and bounded buffers. Core JSON envelope maximum is 4 MiB, batch at most 1,000 item revisions and 10,000 parts/refs per body, with the graph bound above. A larger source remains registrable through file payload and opaque media type; it is not silently truncated into JSON. Ordinary commands return explicit LIMIT_EXCEEDED or INSUFFICIENT_STORAGE before claiming success.

PostgreSQL 18 core is sufficient: uuid, bytea, jsonb, constraints, indexes and transactional locking. No specialized temporal/vector extension is required by this registration baseline. This is not a claim of unbounded throughput; serial publication favors correctness and simplicity for one personal brain. Benchmarks during implementation must report limits rather than silently weaken ordering.
